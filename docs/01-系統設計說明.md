# 系統設計說明

## 一、設計出發點

財務長的失誤幾乎不是「不知道要做什麼」，而是三種結構性破口：

1. **時間破口** — 期限是相對的（「期末後 45 日」、「年度終了後 3 個月」），
   遇到假日還要順延，人腦換算容易錯，也難以提前規劃工作量。
2. **證據破口** — 事情做了，但沒有留下「誰在什麼時候確認了什麼」的軌跡。
   稽核與會計師要的是證據，不是印象。
3. **偵測破口** — 財務比率、法定上限、帳務勾稽差異，多半是季報編製時才發現，
   那時已經來不及調整。

因此系統分成三層，各自對應一個破口：

```
制度層 domain/     ─ 義務主檔、檢核清單、指標字典、規則庫（人可讀、可維護）
        │
邏輯層 engine/     ─ 期程展開、營業日調整、指標解算、規則評估（純函式、有測試）
        │
呈現層 pages/      ─ 工作台、行事曆、財務檢核、治理檢核、風險登錄簿
```

制度層是唯一的事實來源。行事曆的任務、文件的總表、儀表板的統計，全部由它推導，
所以「制度改了、行事曆沒改、文件也沒改」這種常見的內控文件缺失不會發生
（`docs/` 底下的總表由 `src/domain/docs.ts` 渲染，並以測試偵測漂移）。

## 二、資料模型

### Obligation（定期義務）
描述「一件要定期做的事」的制度規則，不含任何具體日期：

```ts
{
  id, title, area,                      // 屬於哪個職能面向
  category,                             // 法令 / 規章 / 契約 / 內部
  tiers,                                // 適用板別（空 = 全部）
  period,                               // 期間切法：月/雙月/季/半年/年/事件驅動
  due,                                  // 到期規則（相對於期間終了日）
  adjust,                               // 遇假日順延 NEXT / 提前 PREV
  leadBusinessDays, remindDaysBefore,   // 提前開工與提醒
  owner, reviewer, approver,            // 三段權責分工
  severity, legalBasis, penalty,        // 風險權重與法源
  channel, outputs, checklist,          // 申報管道、交付物、檢核點
}
```

### Task（任務實例）
由 Obligation × 會計年度展開而成，帶有具體日期與執行狀態。
同時保留 `statutoryDue`（法定期限）與 `dueDate`（營業日調整後），
介面上會標示哪些任務因假日順延——這在爭議時是重要的判斷依據。

### CheckRule（檢核規則）
`指標算式 + 比較子 + 門檻`，門檻本身也可以是算式。

## 三、關鍵設計決策

### 1. 到期規則用「相對描述」而非固定日期
主檔寫的是規則（`{ type: 'DAYS_AFTER', days: 45 }`），不是 5/15。
好處是換會計年度、換成非曆年制公司、改期限規定時，只動一處。

支援三種規則涵蓋台灣實務：

| 規則 | 用途 | 例 |
|---|---|---|
| `DAYS_AFTER` | 期末後 N 日 | 季報 45 日 |
| `MONTHS_AFTER` | 期末後 N 個月（可指定日） | 年報 3 個月、月營收次月 10 日 |
| `FIXED_IN_PERIOD` | 期間內固定日 | 營所稅暫繳 9/30 |

`MONTHS_AFTER` 加月份時會收斂至目標月份最後一日：12/31 + 6 個月 = 6/30，
而不是不存在的 6/31——股東常會期限正是這個情形。

### 2. 營業日調整分方向
法定申報期限遇例假日**順延**（`NEXT`），內部作業期限遇例假日**提前**（`PREV`）。
兩者混用會產生「內部結帳日排在法定申報日之後」這種荒謬排程。

### 3. 不使用 `eval` 執行算式
檢核規則由財會人員維護。若以 `eval`／`new Function` 求值：

- 任何能編輯規則的人，等同能在使用者瀏覽器執行任意程式碼
- 規則寫錯時整個畫面會崩掉，而不是回報「這條規則設定有誤」

因此自製 tokenizer + shunting-yard 解析器（`src/lib/formula.ts`），
只支援 `+ - * / ( )`、一元負號、識別字與 `MIN/MAX/ABS/IF`，其餘字元一律拒絕。

### 4. 「資料不足」是獨立狀態，且要扣分
缺欄位、分母為零一律回傳 `null` 而非 `0`。
若把資料不足當成 0 再去比大小，`0 <= 上限` 會回報「通過」——
這是財務檢核最危險的失敗模式。

`NO_DATA` 在檢核總分中依嚴重度扣分（權重 0.3）：
拿不到資料本身就代表這個控制無法執行。

### 5. 衍生指標採疊代求解
指標會互相引用（`netDebtToEbitda` → `netDebt` → `grossDebt` → 輸入科目）。
`resolveScope` 反覆掃描直到沒有新值產生，因此新增指標時不必煩惱定義順序，
也不會因為循環引用而無限迴圈。

### 6. 存量與流量不可混用
`netDebt / EBITDA` 的分子是期末存量、分母是流量。
若用單季 EBITDA，槓桿倍數會膨脹約四倍。因此分母使用獨立輸入的
`ltmEbitda`（近 12 個月），與聯貸合約定義一致。

### 7. 重新展開行事曆不會弄丟已完成的工作
`mergeTasks` 以 `任務 id = 義務 id :: 期間標籤` 對齊，保留使用者狀態；
主檔新增檢核項目時，既有任務會補上新項目（未勾選），舊勾選不受影響。

### 8. 事件驅動義務不排入行事曆
重大訊息、取得處分資產以「事實發生日」起算，沒有可預先展開的到期日。
硬排入行事曆只會產生假的完成率。這類義務改列於「公司治理檢核」頁作為常備 SOP，
並成為稽核抽核的對象。

## 四、檢核功能的三個層次

| 層次 | 問的問題 | 系統位置 |
|---|---|---|
| 作業層 | 這件事的每個步驟都做了嗎？誰確認的？ | 任務檢核清單（266 個檢核點，含控制點編號） |
| 數據層 | 數字有沒有踩到紅線或異常波動？ | 財務檢核（24 條規則，紅／黃／資料不足三態） |
| 治理層 | 法定成數、關鍵時程、事件應變有沒有缺口？ | 公司治理檢核、風險登錄簿 |

三層互相連結：風險登錄簿的每一筆都指向具體的檢核規則與定期義務，
並即時顯示所連結規則的現況，形成「風險 → 控制 → 現況」的完整鏈路。

## 五、測試策略

引擎層全部是純函式，因此可用單元測試鎖住法規期限這類「錯了代價很高」的邏輯：

- **期限推算**：季報 45 日、年報 3 個月、營所稅 5 月底、股東常會 6 月底、
  營業稅雙月期六期日期、暫繳 9/30、扣繳憑單次年 1/31，逐條驗證
- **營業日調整**：週末與國定假日、順延與提前兩個方向
- **公式引擎**：優先序、一元負號、缺資料回 `null`、除以零回 `null`、
  拒絕非法字元（確認未走 `eval`）
- **規則庫完整性**：所有規則與衍生指標引用的代號都存在於指標字典、
  義務與檢核點 id 全域唯一、每項義務都有法源與負責人
- **主檔合併**：重新展開時保留使用者狀態、主檔新增檢核項目的向後相容
- **文件一致性**：`docs/` 總表與主檔相符

共 79 項測試（`npm test`）。

## 六、擴充指引

| 要做的事 | 怎麼做 |
|---|---|
| 新增一項定期義務 | 在 `src/domain/obligations.*.ts` 新增一筆，行事曆與文件自動生效 |
| 新增一條檢核規則 | 在 `src/domain/rules.ts` 新增；若需要新指標，先加到 `metrics.ts` |
| 新增衍生指標 | 在 `metrics.ts` 加上 `formula`，順序不拘（疊代求解） |
| 調整政策上限 | 系統「設定」頁，不需改程式 |
| 更新國定假日 | `src/lib/date.ts` 的 `HOLIDAYS`（每年須依人事行政總處公告更新） |
| 接 ERP 資料 | 取代 `useCheckInputs()` 的資料來源即可，引擎不需更動 |

## 七、目前的限制

- 資料存於瀏覽器 localStorage，未做多人協作、權限控管與稽核軌跡的伺服器端保全。
  正式導入時，任務狀態與勾稽紀錄應存於具備不可竄改軌跡的後端。
- 國定假日表僅涵蓋 2026–2027，需每年維護。
- 金融保險等特殊行業的申報期限與適用規定未納入，須另行調整。
- 法源與門檻為範本，不構成法律、會計或稅務意見。
